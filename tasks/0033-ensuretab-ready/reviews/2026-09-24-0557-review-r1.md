## Verdict

Changes requested. The end-to-end probe is the right design and most acceptance
boxes are met, but a tab closed while ensureTab is waiting is reported as ready.

## Findings

1. **A closed tab counts as ready.** In `src/core/tabBridge.js`, `probeOnce`
   registers a pending entry whose `reject` resolves `true`. That is meant for
   page.js's error reply to the unknown `__wlReadyProbe` kind. The
   `tabs.onRemoved` listener calls `reject` on every pending entry, so closing
   the tab during `waitUntilReady` makes the probe count as answered. ensureTab
   then resolves with the dead tab while `connectedTabId` is already null.
   Reproduced against 57c6751 with a small fake chrome script: tab 5 reused,
   `onRemoved(5)` fired 10 ms in, result
   `{"resolved":5,"connectedTabId":null}`. Required: a unit test that closes
   the tab while it is still `listening` (shown failing first in the progress
   log), and a fix that tells "the page answered" apart from "the tab went away"
   so that ensureTab rejects with `TabGoneError`.
2. **Progress log name.** `implementation/2026-09-24-ensuretab-ready.md` uses
   the plan's stem with no suffix. The repo convention is
   `<plan-stem>-progress.md` (see
   `tasks/0011-tab-bridge/implementation/2026-09-23-tab-bridge-progress.md`).
   Rename it with `git mv`, and give the superseding plan
   `2026-09-24-1-ensuretab-ready-e2e-probe.md` its own `-progress` log. Put
   both changes in a tasks-only commit. The original plan must stay untouched.
3. **Comment narrating the mock.** The three-line comment in
   `test/tabbridge.test.js`'s fake `sendMessage` (`contentState 'listening'
   ...`) explains the mock rather than recording a constraint. CONTRIBUTING.md
   and GOAL.md rule 4 say no comments by default. Remove it, or turn the
   meaning into names, for example a named state constant. The spec comment
   about `chrome.tabs.create` bypassing `context.route` records a real
   harness constraint and stays.
