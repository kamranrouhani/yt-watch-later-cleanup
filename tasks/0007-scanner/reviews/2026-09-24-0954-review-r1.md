## Findings

1. **Safety: the scanned pages are never checked for the verified sort.** Upstream passes `requireSortOrder: WL_OLDEST_SORT_ORDER` into `fetchAllWatchLaterEntries` (lines 568 to 574, call sites 1348 and 1413) and throws "Sort drift detected" when the first page's own sort state is not order 2. `scan` drops that check, so the only thing tying positions to oldest first is the edit ack. Reproduced: a client whose edit ack reports order 2 but whose `browseWatchLater` serves the real page-1 fixture (its sort state is `{"selectedTitle":"Date added (newest)","selectedOrder":1}`) gets `status complete, entries 300` with positions 1..300 assigned in newest-first order. That is exactly the "random removals" the card's safety label warns about. Required: check the sort state of the first scanned page and refuse (a `SortNotVerifiedError`, or a distinct drift error that #12 can surface) when it is not order 2, returning no entries. Add a test that fails without the check: edit ack confirms, first browse page reports order 1.

2. **Pagination has no seen-token guard.** Upstream tracks `seenTokens` and skips a token it has already consumed. `scan` follows `page.continuationToken` unconditionally. Reproduced: a continuation response that returns its own token again was still being fetched after 50 calls (the probe threw to stop it). A misbehaving response means an unbounded request loop against YouTube. Required: skip a repeated token, with a test.

3. **Throttle between pages is missing.** The issue scope says "throttle between pages". Upstream sleeps `scanPageThrottleMs` (default 50) between continuation fetches when more tokens remain. Nothing in `scan` does this and the plan does not mention it. Required: port it with upstream's default and an option to set it to 0 in tests, or record in a superseding plan why it is dropped.

4. **Aborted scans are returned in the same shape as complete ones.** An aborted scan returns `entries` with positions and a fingerprint, distinguished only by `status: 'aborted'`. The abort box is met, but #12 requires "cancel mid scan leaves the previous saved scan intact", and a partial list with positions 1..k looks like a whole playlist to anything that forgets to check `status`. Not a blocker on its own; make the choice explicit in the plan (a superseding plan, since this one is in use) and consider leaving `fingerprint` null for an aborted scan so #14 can never match against it.

5. **Card rule on the port.** The card asks for an identical port first and a restructure in a separate commit, as PR #37 did. The progress log says the two were combined because upstream calls `youtubeiRequest` directly. That reasoning is fair for the network layer, but the combined commit is also where findings 1 to 3 were lost. No history rewrite needed; the fix commits for 1 to 3 should name the upstream lines they restore, and the progress log should record the deviation and what it cost.
