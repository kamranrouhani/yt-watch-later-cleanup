# Full scan in verified oldest-first order

- **Issue:** #7
- **Branch:** `feature/0007-scanner`
- **Written:** 2026-09-24 09:45, on `main` at `00254c2` (after merging PR #38)
- **Supersedes:** nothing

## Goal

`src/core/scanner.js` with `scan({ innertube, onProgress, signal })` that
sets the Watch Later sort to oldest-first, verifies the server actually
confirms it before trusting any position, then follows continuation tokens
to build the full deduped entry list. `SortNotVerifiedError` when
verification never lands. The result is what #12's dashboard table and
#14's stale-preview check consume.

## Decisions

- **Composition, not another port of the userscript's network code.**
  `innertube.js` (PR #38 era, `createInnertube`) already knows how to call
  `browse`, `browse` with a continuation, and `edit_playlist`; the scanner
  takes an innertube instance as a dependency the way `remover.js` does,
  and never calls `net.js` or builds a InnerTube body itself. The sort
  verification and pagination algorithms are the port target named in the
  issue (`ensureWatchLaterOrderOldest`, `fetchAllWatchLaterEntries`,
  `extractSortState`, upstream lines 418-650, 692), rewritten against that
  dependency shape instead of the userscript's raw `youtubeiRequest`.
- **`extractSortState`** is ported into `scanner.js` (it belongs to sort
  verification, not the parser) with the same walk: find the first
  `sortFilterSubMenuRenderer`, map its `subMenuItems` to
  `{ title, selected, playlistVideoOrder }`, return the selected item's
  order or `null`. Confirmed against the real page-1 fixture: order 2 is
  "Date added (oldest)", order 1 is "Date added (newest)" (the fixture's
  actual selection), order 0 is Manual.
- **Verification protocol**, matching upstream's `ensureWatchLaterOrderOldest`:
  call `editPlaylist([{ action: 'ACTION_SET_PLAYLIST_VIDEO_ORDER',
  playlistVideoOrder: 2 }])`, read the sort state back from *that* edit
  response; if it does not confirm order 2, call `browseWatchLater()` and
  read the sort state from the browse response instead (some accounts only
  echo the confirmed order on the next browse, not the edit ack itself,
  which is why upstream checks both). Retry up to `sortVerifyMaxAttempts`
  (default 6, upstream's constant) with `sortVerifyPollMs` between attempts
  (default 350ms, upstream's constant). Exhausting attempts throws
  `SortNotVerifiedError` before any page is fetched, so a caller can never
  read `entries` off a scan that never verified: `scan` returns nothing,
  not a partial list, in that case.
- **Pagination.** First page from `browseWatchLater()`, each further page
  from `browseContinuation(token)`, parsed with `playlistParser.parsePage`
  (PR #37). Dedupe on `setVideoId` across pages, ordered by first
  appearance (oldest-first sort already guarantees the appearance order is
  the real order). `position` is assigned 1..N over the deduped list after
  the whole scan completes, never per-page, so a duplicate encountered on
  a later page does not shift positions.
- **Cancellation.** `AbortSignal` is checked between pages, before each
  continuation fetch, never mid-fetch (nothing in this codebase makes
  `fetch` itself abortable, `net.js` does not accept a signal and the
  issue only asks for "stops within one page"). The in-flight page always
  finishes and is kept in the result; no further page is requested once
  the signal is aborted. The sort-verification phase runs to completion
  before pagination starts and is not itself interruptible: a caller who
  wants to cancel a scan before it starts should not call `scan` at all.
- **Progress.** `onProgress({ page, pageEntries, totalEntries })` after
  each page, page 1 included, mirroring `fetchAllWatchLaterEntries`'s log
  calls but as data instead of strings.
- **Result shape**, the part #14 depends on:
  ```js
  {
    entries,       // [{ ...Entry, position }], position 1..N
    scannedAt,     // ISO timestamp, taken after the scan finishes
    pageCount,     // pages actually fetched, including page 1
    entryCount,    // entries.length
    fingerprint,   // sha256 hex of the ordered setVideoId list
    sortState,     // the verified { selectedTitle, selectedOrder } from the last check
    status,        // 'complete' or 'aborted'
  }
  ```
  `fingerprint` is computed over `entries.map(e => e.setVideoId).join('\n')`
  with `crypto.subtle.digest('SHA-256', ...)`, the same Web Crypto API
  `auth.js` already uses (available in the dashboard page context and
  under Node 22's global `crypto`, so the module needs no dependency
  injection for it). Any change to the ordered id list, added, removed or
  reordered, changes the digest input and therefore the fingerprint; this
  is what #14's stale-preview check compares against.
- **What the scanner does not do.** No dry-run gating, no rule evaluation,
  no dashboard rendering, no storage write. Those are #8 (merged), #12 and
  #16.

## Fake client for tests

The issue asks for "a fake client serving the captured pages". The fake is
a plain object shaped like what `createInnertube` returns
(`browseWatchLater`, `browseContinuation`, `editPlaylist`), scripted with a
response queue, the same pattern `remover.test.js`'s `fakeInnertube` and
`innertube.test.js`'s `fakeDeps` already use in this repo. No real
`createInnertube` involved: the scanner only needs the three methods, so
the fake never touches `net.js` or `auth.js`.

- The three real captured pages (`test/fixtures/captured/2026-09-24/`,
  disjoint per the playlist-parser plan) prove the "every item once, in
  order, positions 1..N" box at real scale (300 items, 3 real pages) plus
  a synthetic 4th terminal response (no entries, no continuation) to end
  the chain, since the real capture's page 3 does carry a further token
  (`CONTINUATION_3`) that has no corresponding fixture.
- A duplicate-across-pages box needs its own small crafted fixture: the
  real captured pages are disjoint by construction (noted in the
  playlist-parser plan), so proving cross-page dedupe means two minimal
  `playlistVideoListRenderer` pages sharing one `setVideoId`.
- The never-verifies box scripts every `editPlaylist`/`browseWatchLater`
  response to report order 1 (newest) selected, never 2.
- The abort box uses a real `AbortController`, aborts it from inside
  `onProgress` after page 1, and asserts `browseContinuation` was never
  called.
- The fingerprint-changes box scans the same small fixture three times
  with one entry added, removed, and reordered respectively, asserting all
  three fingerprints differ from the base and from each other.
