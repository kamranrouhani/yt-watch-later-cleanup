## Findings

1. Scan does not work in the real extension.
   `dashboard/dashboard.js:233` sends `{ wlRequest: true, kind: 'scan' }`
   through `chrome.runtime.sendMessage`. Nothing listens for `scan`:
   `background.js` only opens the dashboard, and `content/page.js:45-52`
   handles `ping`, `browseWatchLater`, `browseContinuation` and
   `editPlaylist` only. The payload also carries a function (`onProgress`)
   and an `AbortSignal`, which extension messaging cannot serialise. The
   dashboard loads `tabBridge.js` but never calls it, and does not load
   `scanner.js` or `playlistParser.js` at all. Clicking Scan in the loaded
   extension (Playwright, real Chromium) gives:

   ```
   errorText: "Scan failed"
   console.error: Unchecked runtime.lastError: Could not establish connection. Receiving end does not exist.
   tabs: about:blank, chrome-extension://.../dashboard/dashboard.html
   ```

   No YouTube tab is opened, contrary to docs/ARCHITECTURE.md "The dashboard
   needs a YouTube tab". Fix: load `playlistParser.js` and `scanner.js` in
   `dashboard.html`, build `WLCore.tabBridge.createTabBridge(chrome)`, call
   `ensureTab()`, wrap `bridge.request('browseWatchLater' | 'browseContinuation'
   | 'editPlaylist', ...)` as the `innertube` object, and run
   `WLCore.scanner.scan({ innertube, onProgress, signal })` inside the
   dashboard, keeping the `AbortController` local.

2. Acceptance 1 does not test the dashboard's scan path and does not check
   values.
   `test/dashboard.test.js:170-172` runs the scanner in Node and hands the
   finished result to a fake that answers the invented `scan` message, so the
   test passes on exactly the wiring that finding 1 shows broken. The value
   checks are row 0's position and title only (`:188-189`); blanking channel,
   duration, or replacing the status text all stay green. The filter
   assertion at `:198` is `<=`, which holds when the filter does nothing.
   Fix: the fake bridge serves the captured pages at the `chrome.tabs` /
   `tabBridge.request` level, and the test compares every rendered row's
   position, title, link href, channel, formatted duration, watched percent,
   availability and Short marker against `scanner.scan` output for the same
   pages.

3. Acceptance 4 measures no time, and the page does freeze.
   The issue box says "without freezing the page for more than 200 ms per
   interaction (measured in the test)". `test/dashboard.test.js:326-328`
   says timing is not measured, and no assertion reads a clock; a 1 s busy
   loop in `renderTable` stays green. Measured at 5,000 rows in jsdom, three
   runs: title sort 2253 to 2395 ms, reverse 1981 to 2057 ms, duration sort
   2002 to 2130 ms, filter 206 to 212 ms. `renderTable`
   (`dashboard/dashboard.js:130-200`) rebuilds all 5,000 rows on every
   interaction, and `MAX_ROWS_RENDERED` equals the row count, so the
   "virtualized table" described in the PR body does not exist. The fixture
   also uses `Math.random()` (`:292-293`), so the data is not reproducible.
   Fix: render a window of rows (or append in chunks across frames), assert
   `performance.now()` deltas under 200 ms for each sort and filter
   interaction, and use deterministic synthetic values. Round 2 noted the
   missing measurement as a limitation and approved anyway; it is the
   acceptance box itself.

4. A scan response that arrives after Cancel overwrites the saved scan.
   `cancelScan` (`dashboard/dashboard.js:251-258`) aborts the signal but the
   response callback at `:234-247` still writes whatever arrives. The scanner
   answers an abort by returning a partial list with `status: 'aborted'`
   (`src/core/scanner.js:160-161`), not by throwing, so the late write is the
   normal case once finding 1 is fixed. Probe against HEAD:

   ```
   after cancel, stored title: Saved
   after late aborted response, stored title: Partial status: aborted
   ```

   The acceptance 3 test cannot see this: its bridge never answers
   (`test/dashboard.test.js:238-244`), and a mutation that writes a partial
   scan to storage on cancel stays green because the test only checks
   `hidden` flags. Fix: in the completion path, drop the result when the
   controller was aborted or `scan.status !== 'complete'`, and make the test
   answer after cancel with an aborted result, then assert the stored scan
   and the rendered rows are still the old ones.

5. Acceptance 2 cannot fail on a rescan.
   `test/dashboard.test.js:221` passes `null` as the bridge, so any rescan
   call hits the no-bridge stub, and the test never counts scan requests. A
   mutation that fires a scan on open stays green. It also asserts only the
   row count, not the age text or the Rescan button. Fix: pass a bridge that
   counts requests and assert zero, and assert `#saved-info` shows the age.

6. Scan errors lose their type.
   `dashboard/dashboard.js:239` wraps every failure as
   `new Error(response.error.message)`, so `error.name` is always `Error` and
   the switch in `showError` (`:81-99`) never matches. The error test passes
   only because the raw message "Could not verify sort" happens to contain
   "sort" (`test/dashboard.test.js:371,387`). The issue's three named types
   are not handled: not signed in (`AuthError`) and rate limited
   (`RateLimitedError`) from `src/core/innertube.js:17-18` have no case.
   Fix: keep the real error object from the scanner, add cases for
   `AuthError` and `RateLimitedError`, and assert the exact message per type.

7. Sort header labels accumulate arrows and show the wrong direction.
   `dashboard/dashboard.js:272-273` uses `/s*$/`, which matches the letter
   `s`, not whitespace, so each click appends another arrow. After title,
   title, duration the headers read `"Title ▼ ▲"` and `"Duration ▼"`, and
   the old column keeps its arrow. The first click sorts ascending but shows
   ▼, and `data-active-sort` is always `asc` (`:271`). Fix: keep the label in
   a data attribute, rewrite `textContent` from it for every header on each
   click, and set the arrow and `data-active-sort` from `sortDir`.

8. The dashboard reimplements storage instead of using `src/core/storage.js`.
   `dashboard/dashboard.js:32-57` is a second envelope wrapper without the
   quota handling that storage.js provides, and it silently becomes a no-op
   store when `chrome.storage` is missing. ARCHITECTURE.md says a failed
   write must degrade to a warning. Fix: load `src/core/storage.js` and use
   `WLCore.storage.createStorage(chrome.storage.local)` with `KEYS.scan`,
   showing the `warning` when `set` returns `ok: false`.

9. Progress does not report what the issue asks for.
   `updateProgress(page, pageEntries, totalEntries)` (`:219-224`) takes
   positional arguments, but the scanner calls `onProgress({ page,
   pageEntries, totalEntries })` (`src/core/scanner.js:152,173`). Wired to
   the real scanner it would print `Page [object Object], undefined items`.
   The fake bridge calls it positionally (`test/dashboard.test.js:34`), which
   hides the mismatch. The bar width formula (`page / 3`, then
   `totalEntries / 5000` capped at 95) has no relation to real progress.
   Fix: destructure the object, show pages and items, and assert the text
   in a test driven by the real scanner.

10. The tests do not load `dashboard.html`.
    `test/dashboard.test.js:71-92` carries its own copy of the markup, so an
    id renamed in `dashboard.html` breaks the page and keeps the tests
    green. Fix: read `dashboard/dashboard.html`, strip the `<script>` tags,
    and use it as the JSDOM source.

11. Thumbnails load from `i.ytimg.com`, which the no-network rule does not
    list.
    `dashboard/dashboard.js:145` sets `img.src` to the entry's thumbnail URL.
    CONTRIBUTING.md allows only `www.youtube.com` and `www.googleapis.com`
    and says no third-party image is loaded; the issue asks for a thumbnail
    column. `test/no-network.test.js` does not check image sources, so it
    passes. This needs Kamran's decision: allow `i.ytimg.com` in the rule and
    the guard test, or drop thumbnails from #12.
